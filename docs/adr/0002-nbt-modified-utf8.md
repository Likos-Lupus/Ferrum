# ADR-0002: NBT strings use Modified UTF-8

- Status: Accepted
- Date: 2026-09-23
- Affected modules: FerrumNbt

## Context

Minecraft NBT string serialization uses Java's `DataInput.readUTF` / `DataOutput.writeUTF`, which
encode strings as **Modified UTF-8 (MUTF-8)**, not standard UTF-8. Standard assumptions about UTF-8
(a SIMD UTF-8 validator, standard surrogate handling, standard `U+0000` encoding) do not fully match
MUTF-8 and would produce wrong bytes or reject valid input.

## Decision

NBT strings are decoded and encoded as Java Modified UTF-8, matching `readUTF`/`writeUTF`
semantics exactly.

1. Implement a dedicated MUTF-8 decoder/encoder in the native kernel.
2. The ASCII range may use a vectorized fast scan.
3. Test `U+0000`, surrogate pairs, and the Java length limits according to Java modified-UTF
   semantics.
4. Use a golden corpus generated by Java `writeUTF`/`readUTF` and verify both directions.

## Alternatives considered

- Treating NBT strings as standard UTF-8: rejected; it changes bytes for `U+0000` and surrogate
  handling and breaks byte-for-byte interoperability.
- Falling back to Java for all string handling: rejected as the default; it is retained only as the
  fallback path.

## Performance evidence

No performance commitment in this record. Any vectorized ASCII path is validated by the NBT
benchmarks before it is enabled by default.

## Correctness / compatibility impact

Byte-exact round-trip with vanilla NBT is required in both directions. A mismatch is a correctness
failure, not an acceptable approximation.

## Rollback

Disable the NBT string fast path per module via configuration; the Java path then handles all
strings. The decision itself is changed only by a superseding ADR.

## Follow-up work

- Build the MUTF-8 golden corpus.
- Wire the corpus into JUnit 6 differential tests and the fuzz targets.
